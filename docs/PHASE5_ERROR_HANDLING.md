# Apex AI Phase 5 — Error Handling Foundation

- **Completed:** 2026-08-29 (America/Chicago)
- **Baseline:** `25d26c2` (Phase 4 dependency audit)
- **Scope:** public backend errors, streaming failures, browser handling, compatibility UI,
  and command-line boundaries

## Outcome

Phase 5 establishes one public error contract without replacing the existing RAG, LLM,
document, memory, or UI implementations. Normal API and UI responses no longer interpolate
unexpected exception values, exception class names, or tracebacks.

The implementation preserves existing string-valued JSON `detail` responses for
application errors while adding a structured `error` object for new clients:

```json
{
  "detail": "The requested record is missing.",
  "error": {
    "code": "not_found",
    "message": "The requested record is missing.",
    "retryable": false
  }
}
```

Validation failures add bounded field metadata without returning Pydantic's submitted
`input` values or internal context:

```json
{
  "detail": "Check the submitted fields and try again.",
  "error": {
    "code": "validation_error",
    "message": "Check the submitted fields and try again.",
    "retryable": false,
    "fields": [
      {
        "field": "question",
        "message": "Field required",
        "code": "missing"
      }
    ]
  }
}
```

The exact field message is generated by the installed Pydantic version and is not a stable
programmatic identifier. Clients should use `error.code` and each field's `code`.

## Findings before Phase 5

A useful `ApexError` hierarchy already represented expected configuration, provider,
database, document, and security failures. That code was retained. The audit found several
inconsistent transport boundaries around it:

- routes returned a mix of FastAPI's default `detail` strings, validation arrays, and
  manually formatted `ApexError` text;
- no application-wide handler normalized unexpected API exceptions;
- provider failures returned status 500 even when the dependency/provider was the failing
  boundary;
- NDJSON stream failures had only a message and exposed the Python exception class for
  unexpected failures;
- runtime startup fallback text embedded an unexpected exception class and value;
- the browser displayed arbitrary native JavaScript `Error.message` values and separately
  implemented HTTP parsing for normal requests and streaming;
- Gradio chat and ingestion callbacks interpolated unexpected exception details; and
- terminal chat printed unexpected exception values directly.

These were presentation and boundary problems. No evidence required replacing backend
providers or changing retrieval behavior.

## Backend foundation

### Expected application errors

`ApexError` now adds two stable class attributes:

- `code`: a snake-case category such as `provider_error` or `database_error`;
- `retryable`: a conservative hint, not an instruction to retry automatically.

The established `user_message()` remains available to trusted local/developer tools for
compatibility. Public transports use `public_message()`, which always omits `WHY`: existing
adapters often store dependency exception text there, and even directly authored reasons
can drift toward diagnostics over time. The actionable `WHAT HAPPENED` and `HOW TO FIX`
sections remain.

Those public sections pass through a conservative final sanitizer for traceback and
exception-class signatures, credential-shaped values, configured endpoints, and local
filesystem paths. Developers must still author `what` and `fix` for users rather than rely
on the sanitizer as a substitute for safe error design.

### HTTP exception handlers

`apex_ai/api/errors.py` installs handlers for:

| Failure class | Public handling |
|---|---|
| Explicit `APIError` | Preserve its reviewed status, code, message, retry hint, and headers. |
| Starlette/FastAPI HTTP error | Normalize lower-status failures into the shared envelope and sanitize legacy string details. Unreviewed 5xx details are replaced with a generic message. |
| FastAPI/Pydantic request validation | Return status 422, `validation_error`, and at most 20 field issues without submitted values. |
| Uncaught `ApexError` | Map the known category to an HTTP status and use its public representation. |
| Unexpected `Exception` | Log internally and return generic `internal_error`; never serialize the exception. |

Handlers are installed once by `create_api()` and therefore cover root routes, included
routers, missing routes, and method errors.

### Default expected-error status mapping

| Apex category | Default HTTP status | Retry hint |
|---|---:|---|
| Provider failure | 502 | yes |
| Configuration, database, missing embedding model, unavailable reranker | 503 | class-specific |
| Embedding/index mismatch | 409 | no |
| Document, model-selection, and security rejection | 400 | no |
| Unknown Apex subclass | 500 | class-specific |

Route-specific `APIError` values can deliberately override this mapping. Phase 5 does not
add retries, backoff, or background recovery merely because `retryable` is true.

### Service-not-ready behavior

Chat, document, and upload routes now return a reviewed `service_not_ready` message that
directs the user to Settings. They no longer copy `services.startup_error` into every
failed operation. Expected startup guidance remains available in the existing app-config
and Settings surface.

Unexpected startup and optional-memory initialization failures now retain their traceback
only in internal logging and expose the shared generic message in runtime state.

### Streaming parity

An HTTP error before streaming begins uses the normal JSON envelope. Once an NDJSON
response has started, its error event carries the equivalent problem object while retaining
`message` for compatibility:

```json
{
  "type": "error",
  "message": "LLM PROVIDER ERROR\n\nWHAT HAPPENED:\nThe configured provider failed.\n\nHOW TO FIX:\nCheck the provider and try again.",
  "error": {
    "code": "provider_error",
    "message": "LLM PROVIDER ERROR\n\nWHAT HAPPENED:\nThe configured provider failed.\n\nHOW TO FIX:\nCheck the provider and try again.",
    "retryable": true
  }
}
```

Unexpected generator failures use `internal_error`. No synthetic answer, source, or
citation is generated on the failure path.

### Upload cleanup

The upload route now places readiness checks, filename validation, staging, ingestion, and
all explicit upload errors under one `try/finally` boundary. The framework upload handle is
closed and an allocated staging directory is removed for successful and failed requests.
Expected application failures flow through the same central handlers as other routes.

## Frontend foundation

The browser now has one `ApexAPIError` type and one response parser for ordinary requests
and stream startup:

- structured backend problems preserve `code`, `status`, `retryable`, and field issues;
- legacy 4xx `detail` strings remain readable when they do not match diagnostic, credential,
  endpoint, or local-path signatures;
- legacy/unstructured 5xx responses and unstructured stream failures use status-safe text;
- fetch rejection becomes a stable `network_error` instead of displaying a browser/vendor
  message;
- malformed successful JSON becomes `invalid_response`, while malformed stream data reaches
  the same generic visible-error boundary;
- unknown native JavaScript errors resolve to a generic user message; and
- every visible catch path uses the safe message boundary.

Messages continue to use text nodes or the existing escaped error renderer. Phase 5 does
not automatically retry writes, uploads, deletion, model selection, or chat generation,
because doing so can duplicate non-idempotent operations.

The Gradio compatibility UI now uses the same public `ApexError` form and generic unexpected
message. Handled terminal-chat and per-file batch-ingestion failures also stop printing
unexpected exception values. The evaluation command keeps technical tracebacks in
application logs while showing a non-diagnostic terminal message.

## Compatibility decisions

- Route paths, request models, successful response payloads, public Python entry points,
  providers, and persistence formats are unchanged.
- Existing string-valued `detail` responses remain strings so the established browser and
  simple API clients continue to work.
- FastAPI's former validation-detail array is intentionally replaced by a public summary
  string; sanitized field issues move to `error.fields` without submitted `input` values.
- New clients should consume `error.code`; English message text may improve over time.
- Existing low-status custom messages such as “Conversation not found” are preserved.
- Expected provider failures from `/query` now use 502 rather than an undifferentiated 500.
- Expected database/configuration availability failures use 503, while index mismatch uses
  409. These statuses distinguish corrective action without changing backend behavior.
- Developer RAG diagnostics remain separately gated by `APEX_RAG_DEBUG`; Phase 5 does not
  expose them in normal errors.

## Security properties tested

Tests place unique canaries inside:

- a raw unexpected API exception;
- a lower-level exception chained into `ProviderError`;
- invalid submitted request data;
- an unexpected runtime startup exception;
- a failed streaming provider;
- direct expected-error text containing POSIX and Windows paths, an internal endpoint, an
  exception representation, and a credential-shaped value; and
- native browser/network, legacy low-status/500, and unstructured stream error objects.

The canaries, paths, endpoint, credential, `RuntimeError`, and `Traceback` do not appear in
public HTTP, stream, runtime, or browser messages. The test suite also confirms that
`detail` and `error.message` agree, retry metadata is Boolean, and validation reports the
field without echoing its submitted value.

## Boundaries and remaining unknowns

- Browser behavior was exercised through deterministic JavaScript helper execution and
  FastAPI integration tests. Visual/device behavior in Safari, Firefox, and mobile browsers
  is **UNKNOWN** until real-browser testing is available.
- Phase 5 keeps tracebacks internal, but a comprehensive secret-redaction policy for log
  records belongs to Phase 6. Whether every third-party exception is free of credentials
  before reaching existing logs is **UNKNOWN** and is not claimed here.
- The error envelope is a compatibility foundation, not a versioned API specification.
  OpenAPI response schemas and broader endpoint normalization belong to Phase 7.
- `retryable` describes the category only. Safe automated retries, idempotency keys, retry
  delays, and provider-specific recovery remain **UNKNOWN/not implemented**.
- Errors that occur after an HTTP stream has begun cannot change its status code; clients
  must inspect NDJSON error events.
- Crash handling outside Python's normal exception model—process termination, out-of-memory
  kills, native-library aborts, power loss, and disk corruption recovery—is **UNKNOWN**.
- Debug logs remain local operator data and are not suitable for normal-user display.

## Phase 5 conclusion

Apex now has a shared failure vocabulary and safe public boundaries across HTTP, NDJSON,
the main browser client, Gradio, and command-line entry points. Expected failures remain
actionable, unexpected failures remain diagnosable in logs, and normal users no longer
receive raw exception details. This foundation is ready for the separate Phase 6 logging
audit; Phase 5 itself does not claim that logging is fully structured or secret-safe.
