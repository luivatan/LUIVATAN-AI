# Apex AI Phase 90 — Billing Testing: Decision

- **Decided:** 2026-08-30 (America/Chicago)
- **Baseline:** `3470471`, immediately following Phase 89 (Billing Portal decision)
- **Roadmap text:** "Test successful payments, failed payments,
  cancellations, renewals, upgrades, downgrades, and webhook failures."
- **Decision: not implemented in this phase, and correctly so.** Every
  scenario the roadmap names here is a real payment provider's event
  (Phases 85/86/89, all declined this pass). There is no payment flow, no
  webhook, and no provider-managed subscription lifecycle in this codebase
  to write a test against — a test suite exercising "successful payment"
  or "webhook failure" against nothing would have to fabricate the very
  thing it claims to verify.

## Why this can't be done for real right now

Testing a payment scenario for real means asserting against the real
system's real behavior — the same standard every other test in this
project's suite already holds itself to (real SQLite stores, real mocked
HTTP round trips with correctly-shaped payloads verified against actual
provider documentation, never a hand-waved stand-in). Writing tests for
"successful payment," "failed payment," "renewal," or "webhook failure"
today would mean one of two dishonest paths:

1. **Inventing a fake payment provider double** and testing that the
   *fake* reports success/failure correctly — which proves nothing about
   how this application would behave against the real provider Phase 85
   never connected.
2. **Asserting against `SubscriptionStore` directly** (e.g. "calling
   `set_plan()` changes the plan") — which is not a payment test at all.
   That exact behavior is *already* thoroughly tested (see below); relabeling
   it as "payment testing" would be a description that doesn't match what
   the test verifies.

## What is already tested for real, right now

Every real, decision-only piece of Phase 81-84/87-88's architecture has
its own tests today — this is not an untested corner of the codebase, it's
specifically the *payment-provider* scenarios that have nothing to test:

- **28 tests** in `tests/test_billing.py`: plan definitions and
  fallback behavior, `SubscriptionStore` CRUD/isolation/`cancel()`
  semantics, `UsageStore` recording/monthly-period aggregation/isolation,
  and `EntitlementService`'s capacity/rate checks including the
  "upgrading the plan raises the effective limit" round trip.
- **11 tests** in `tests/test_api_ui.py`: the `GET /billing/plans`/
  `GET /billing/plan` endpoints, real enforcement (collection/project/
  document/message limits actually blocking a request with HTTP 402),
  upgrading a plan lifting a previously-hit limit through the real API,
  usage actually being recorded on a real chat message and *not*
  double-recorded on regenerate, and `GET /billing/usage` reporting real
  counts.

"Cancellation" in the sense this codebase can actually deliver
(`SubscriptionStore.cancel()` reverting to the free plan) is covered by
`test_cancel_reverts_to_the_free_plan`. "Upgrades"/"downgrades" in the
sense of `set_plan()` changing which limits apply are covered by
`test_set_plan_persists_and_get_reflects_it` and the API-level upgrade
test above. What's untested is exactly and only what doesn't exist:
a real payment succeeding or failing, a real renewal, and a real webhook
delivery failing.

## What would make this real

Once Phase 85 (payment provider) and Phase 86 (webhooks) exist:

1. Test-mode payment scenarios the provider itself supports for exactly
   this purpose (Stripe, for example, documents specific test card numbers
   for success/decline/3-D-Secure-required cases).
2. Real webhook payloads — either replayed from the provider's own test
   dashboard or generated by triggering real test-mode events — verified
   against the real signature-verification code Phase 86 would add.
3. A webhook-failure test that asserts the *specific* failure-handling
   behavior Phase 86 implements (e.g. idempotent re-delivery, a malformed
   payload being rejected) rather than a scenario invented independently
   of what that phase actually builds.

## Deliberately not done in this phase

- **No payment-scenario test suite against a fake/mocked payment
  provider.** Would test the fake, not the application's real integration
  with anything.
- **No webhook-failure tests.** No webhook handler exists yet (Phase 86)
  to have a failure mode.
- **No renaming of existing `SubscriptionStore`/`EntitlementService` tests
  to imply they cover "billing testing" in the roadmap's sense.** They are
  accurately described above as what they actually verify.
